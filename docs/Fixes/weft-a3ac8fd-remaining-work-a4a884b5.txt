NEW DEFECTS FOUND THIS ROUND
N1 REPRODUCED. Masked recurrent path breaks for batch size > 1.
   weft/modeling_weft.py:227 builds mask_weight as (b, s, 1, 1); lines 238 and 302 index it as mask_weight[:, t, :, :] giving (b, 1, 1), and lines 246 and 310 squeeze to (b, 1). Broadcast against state/output tensors of shape (b, num_state_heads, ...) aligns the batch dim with the head dim. With b=3, num_state_heads=2: RuntimeError ("size of tensor a (3) must match size of tensor b (2) at non-singleton dimension 1"). With b=2, num_state_heads=2 it runs silently but applies each batch item's mask to the wrong head: masked batch-2 vs batch-1 logits differ by 0.0377, and a left-padded batch differs from its unpadded single sequence by 0.0260. The new invariance test only covers b=1, so it cannot see this.
N2 REPRODUCED. Hugging Face generate() bypasses WeftCache.
   WeftCache is only created when the model itself instantiates the cache (modeling_weft.py:410-411). transformers 5.20.2 generate() pre-creates a plain DynamicCache (model._supports_default_dynamic_cache() is True and no _get_cache override exists), so real generation runs on DynamicLayer: physical KV storage grows unbounded (16 tokens stored with window 4) and reorder_cache does not reorder weft_recurrent_state - a reordered-then-decoded batch differs from recomputed prefixes by 1.7158. Items 2 and 4 are therefore fixed only on the WeftCache path; the actual HF generation path keeps both old defects. Single-path direct calls (serving engine) do get WeftCache and are correct.
N3 STATIC. Shipped checkpoint metadata still marks ordinary characters as BOS/EOS.
   weft_shakespeare_ckpt/config.json:5,7 and generation_config.json:3,4 carry bos_token_id=1 (" ") and eos_token_id=2 ("!"). Class defaults are now None (configuration_weft.py:24-26), but the checkpoint's own config overrides them, so generate() with the shipped checkpoint still terminates on "!". The vocab mapping itself (vocab.json) is fine and unchanged.

MATHEMATICAL-USE NOTE (design-intent mapping)
Per the stated design intent, WEFT's use of the supplied uncrossing mathematics is a factorization-based design relationship, and the source supports reading it that way: an exact Boolean uncrossing identity is verified in-repo (tests/verify_identity.py: all 16 single-bit assignments, plus normalized projector idempotence and SWAP = I - 2|s><s|), and the neural layer combines positive learned write features (proj_k), signed learned read features (proj_v), per-rank exponential decay (gamma = sigmoid(decay_logits)) and local sliding-window softmax (modeling_weft.py:215-235, 284-312). The review findings above concern implementation fidelity of that design (caches, masks, kernels, evidence), not the validity of the construction; nothing here treats the absence of literal discrete uncrossing calls in the forward pass as non-use. The one mathematical defect is documentation-level only: the README's normalization (item 6 above).

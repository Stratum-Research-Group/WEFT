  paper/paper.md now says "bounded local window KV cache plus a constant
  16-128 KB recurrent state per layer" (abstract item 2), and section 4.3
  states the 65,536-byte recurrent state plus a bounded W=128 window KV,
  total under ~1.1 MB per layer. The earlier "65 KB is the whole story"

PARTIALLY ADDRESSED 3. Held-out AMW comparison.
  benchmarks/benchmark_amw_rigorous.py now has the right design intent:
  identical prefetched batches, fixed seed 42, validation batches taken from
  stream offset 5000, and held-out val loss/perplexity reported. Paper 4.5
  now cites held-out numbers (7.9944 vs 8.0575, delta 0.063) instead of a
  training-batch "zero loss penalty" claim.
  But split isolation is not yet guaranteed, so treat the held-out numbers
  as approximate until repaired (actionable fix in item 6c):
  a) Validation uses the same streamer and the same get_batch() path.
     Leftover tokens from training-range rows remain in token_queue after
     the last training batch, so the first validation batch can contain
     leftover training-row tokens.
  b) If a fetch raises during validation prefetch, _fetch_next_rows resets
     the offset to 0 and validation silently continues on training-range
     rows (same code path as item 6a). Normal-path disjointness holds only
     when no fetch exception occurs.
  c) Disjoint row offsets do not establish content deduplication:
     FineWeb-Edu rows can repeat content across offsets.
  Measured normal-path facts: 50 training steps x batch 4 x seq 128 =
  25,600 tokens, covered by the first ~36 rows (checked against the live
  FineWeb-Edu rows API, first fetch of 100 rows at offset 0-100);
  validation prefetch starts at offset 5000.
  Remaining caveat: 50 steps, ~25.6k tokens, one seed. "Near parity" at
  this scale is suggestive, not established.

FIXED 4. Needle recall success criterion (with precise scope).
  benchmarks/evaluate_benchmarks.py evaluate_needle_recall() line 62 now
  requires success = "8472" in gen_text, replacing the previous

  it can false-positive if "8472" appears as a substring of a longer digit

1. TEST SUITE FAILS ON GPU-LESS ENVIRONMENTS - root cause reproduced locally.
   File: tests/test_serving_server.py, line 10:
       load_model("weft_shakespeare_ckpt", device="cuda")
   The fixture hardcodes CUDA. On any machine without CUDA (including
   GitHub's ubuntu-latest runners), all 4 serving tests error at fixture
   setup with:
       AssertionError: Torch not compiled with CUDA enabled
   Reproduced locally on CPU-only torch: same 4 errors at the same fixture.
   This is consistent with tonight's seven failed CI runs (one matrix job
   failed, two cancelled; GitHub matrix fail-fast cancels siblings), but the
   individual CI job logs were not inspected, so this root cause is confirmed
   for the local failure and is the likely, not proven, cause of every
   historical run.
   How the CPU path was verified without editing the repo: a standalone
   script imported weft.serving_server, called
   load_model("weft_shakespeare_ckpt", device="cpu") directly, and exercised
   the same four behaviors the tests assert via fastapi.testclient.TestClient:
   /health returned 200 with status "ready", /v1/models listed
   "weft-causal-lm", non-streaming chat completion returned non-empty
   content, and streaming completion returned text/event-stream ending in
   [DONE]. No source or test files were modified.
   Suggested fix: drop the device argument, or use
       device="cuda" if torch.cuda.is_available() else "cpu"
   Projected totals after that fix (projection, not yet measured through
   pytest): 24 collected, 20 passed, 4 skipped, 0 errors. Confirmation still
   requires pushing the fix and watching a CI run.

2. Paper self-contradiction on the 1B result.
   README and docs/BENCHMARK_1_BILLION_TOKENS.md report the author's actual
   continuous run (72.26s, 13,839,492 tok/s, 648.3 MB). But paper/paper.md
   still says "extrapolating to 1-billion tokens in under 1.3 minutes"
   (abstract item 1, ~line 16) and lists "Extrapolated 1-Billion Token
   Scaling: 75.48 seconds" (section 4.2, ~line 130). The paper now
   underclaims and disagrees with the README. Update paper.md and paper.tex
   to cite the measured run, keeping 75.48s only as the older extrapolation.

3. Speedup comparison lacks causal/backend matching (still open).
   benchmarks/ramp_up_benchmark.py (~lines 75-84) benchmarks the SDPA
   baseline without is_causal=True, while WEFT's production attention path
   is causal, and the baseline's backend selection is left to PyTorch
   defaults. The headline "430.7x speedup at N=524,288" (paper 4.1)
   therefore comes from a comparison that is neither causal-matched nor
   backend-recorded. The direction and size of the correction are unknown
   until measured. Fix: rerun the baseline with is_causal=True, and force
   or at least record which SDPA backend the baseline ran on (flash /
   mem-efficient / math, e.g. via torch.nn.attention.sdpa_kernel), since
   backend choice materially changes baseline latency. WEFT's recurrent
   path runs its own kernel and does not need to share that backend. Then
   report the measured matched-causal numbers.

4. AMW computes a dense softmax over ALL memory slots plus a dense D-by-D
   gate (standing; decide and document).
   weft/associative_weight.py forward(): softmaxes affinities over every
   slot and blends all values; self.gate = nn.Linear(hidden, hidden) is a
   full dense projection. Per-token compute is O(DR + MR + MD + D^2):
   encoder projection DR, affinities MR, value blend MD, gate D^2. The 5.2x
   parameter reduction is real; the "selective retrieval" intuition is not
   what the code computes, and the 3.1x-4.1x latency figures are
   author-measured only. If dense-soft readout is the intended design, one
   sentence in the paper stating the read is dense over slots with this cost
   closes the item.

5. "100% exact retrieval up to 16,384 tokens" is a trained probe, not
   zero-shot LM recall.
   benchmarks/benchmark_associative_recall.py train_and_eval() trains a
   fresh probe for 100-120 epochs to ~0.0000 loss on the tested key/value
   bindings at each sequence length. This shows a trained probe can pass the
   finite set of trained bindings that were tested; it does not show that a
   pretrained WEFT LM recalls arbitrary bindings zero-shot. The new
   curriculum pipelines (examples/train_needle_mastery.py,
   train_needle_tuning.py, train_generalized_induction.py) aim at that; the
   open gate is exact-answer recall from a trained checkpoint on random
   held-out passcodes at multiple depths.

6. FineWebEduStreamer robustness (minor).
   weft/dataset_fineweb.py:
   a) _fetch_next_rows() resets current_offset = 0 on ANY exception,
      including transient timeouts, silently recycling training rows from
      the start with no signal.
   b) get_batch() loops forever with 0.5s sleeps if fetches keep failing; a
      training run hangs silently instead of erroring.
   Fix: reset the offset only on a genuine end-of-data response, and add a
   retry cap that raises after N consecutive failures.
   c) ACTIONABLE - Split isolation in benchmark_amw_rigorous.py (repairs
      Partially Addressed 3): before validation prefetch, clear or replace
      the streamer's token_queue so no training-row tokens carry into
      validation batches, and route validation through an exception-guarded
      offset (or a separate streamer instance pinned at offset 5000) so a
      transient fetch error cannot recycle training rows into the held-out
      set. Keep the identical-batches and seed-42 design exactly as-is;
      this repair only changes queue/offset hygiene. Re-report the held-out
      numbers after the fix, since the current delta (0.063) may shift.

7. Quality gate at scale still open (the persuasive result).
   AMW parity evidence is 50 steps / ~25.6k tokens / one seed;
   examples/train_weft_125m_foundation.py exists but no trained-checkpoint
   results are reported yet. The result that would carry the paper's claims:
   a frozen WEFT checkpoint with useful held-out perplexity AND exact-answer
   long-context recall, at materially lower memory/time than a matched dense
   baseline, across seeds. Until then, keep "near parity" and "resolves
   memory drowning" scoped as demonstrated.

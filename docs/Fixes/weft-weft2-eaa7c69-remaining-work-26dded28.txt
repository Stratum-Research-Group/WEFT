1. HIGH - Titans fast weights are silently inert during generation.
   [reproduced here]
   File: weft/modeling_weft.py.
   The single-token decode fast path at line 362
   ("if s == 1 and recurrent_state is not None:") returns at line ~390
   BEFORE the Titans block at line 480. During cached decode:
   - Titans output is never added to global_out, and
   - the Titans fast state (W1, m1) never advances.
   Measured on CPU @ eaa7c69 (use_titans=True, titans_mem_dim=32,
   40-token sequence, prefill 30 + decode steps):
   - weft_titans_state bit-identical before and after 5 decode steps
     (W changed: False, m changed: False);
   - decode logits bit-identical with Titans force-disabled
     (allclose: True), while prefill logits differ (so Titans is active
     in prefill only).
   Consequence: every generated token after the prompt ignores the
   Titans memory the model built during prefill. Any decode-side
   benchmark or demo of "test-time plasticity" is measuring a model
   with that feature switched off, and the cached titans state carried
   in WeftCache (weft/cache.py:28) is dead weight at decode.
   Same root cause, tuple-cache mode: line 388 returns a 2-tuple
   (new_state, next_kv) while the sequence path line 493 returns a
   3-tuple including titans state, so tuple-mode decode silently drops
   the Titans state too.
   tests/test_moe_titans.py:42 only asserts output shapes, so it passes
   with the feature inert.
   Design gate before fixing: Titans prefill applies ONE coupled update
   per chunk against the chunk-start state (chunk-mean gates,
   scale=1/c_len), so decode-time outputs would not necessarily equal a
   single full-forward pass even with Titans wired into decode - the
   update schedule depends on chunk boundaries. Do not prescribe or
   test for full-forward equality. Instead: (a) decide the intended
   decode-time update semantics (e.g. one update per token, or per
   accumulated chunk) and document how it relates to the prefill chunk
   schedule; (b) wire titans_mem into the s == 1 path per that decision,
   storing next_titans_state into the HF cache layer and the tuple, as
   the sequence path does at lines 480-493; (c) add a regression test
   that compares decode against a reference implementation using the
   SAME update schedule, plus an assertion that the cached titans state
   changes after a decode step (the minimal guard against this exact
   regression).

2. MEDIUM - Claimed Titans "parallel prefix scan" does not exist.
   [static]
   Files: weft/titans.py:12-18 (docstring), paper/paper.md section 5
   item 3 ("enabling exact chunkwise parallel prefix scans during
   prefill"), paper.tex WEFT-2 section.
   The docstring advertises a "closed-form associative chunk-parallel
   prefix scan in O(log C) parallel depth" and the constructor takes
   use_scan=True (titans.py:36,44), but forward() never references
   use_scan (verified by source inspection): the implementation is a
   sequential Python loop over chunks with ONE coupled update per chunk
   (gradients and chunk-mean gates computed once against the
   chunk-start state, titans.py:113-141). Two gaps between claim and
   code:
   a) no parallel scan exists anywhere - sequential O(C) chunk loop;
   b) tokens inside a chunk do not see each other's updates, so the
      per-token recurrence in the docstring is not what is computed
      either (it is a chunk-batched approximation with scale=1/c_len).
   Suggested fix: either implement the scan or rewrite the docstring
   and paper sentence to describe the actual chunked single-update rule
   and delete/neutralize use_scan. Also add a test comparing chunked vs
   per-token reference so the approximation error is measured, not
   assumed.

3. MEDIUM - Paper claims MLA cuts KV cache footprint 3.5x; the cache
   stores full up-projected K/V, not latents. [static]
   Files: weft/modeling_weft.py:307-308 (cache.update(k, v, ...) is
   called with the up-projected full-size k and v), weft/cache.py:39-56,
   paper/paper.md section 5 item 1.
   MLA's memory benefit in the DeepSeek design comes from caching the
   low-rank latent c_kv. Here the latent is expanded to full K/V first
   and the FULL tensors are cached. For the WEFT-2 config (window=128,
   16 heads, head_dim=56, bf16) that is 455,168 bytes/layer cached,
   versus 48,768 bytes/layer if latents were cached - the claimed
   compression is not realized anywhere in the serving path. The window
   bound already caps absolute size, so the practical impact is small,
   but the paper sentence is currently wrong about what the code does.
   Suggested fix: either cache c_kv and up-project on read (real MLA
   savings) or reword paper.md item 1 to "reduces projection compute /
   parameter count", not cache footprint.

5. MEDIUM - The new needle benchmarks do not measure needle recall, yet
   the paper cites them for > 0.92 routing affinity. [static]
   a) benchmarks/benchmark_weft2_suite.py:122-155 ("ASSOCIATIVE
      NEEDLE-IN-A-HAYSTACK ROUTING VERIFICATION") places a needle, runs

   b) benchmarks/benchmark_associative_needle_deep.py:85 computes its

      outputs.logits[:, -1, :config.hidden_size] - i.e. it slices the
      first 256 entries of the LM's VOCAB logits (vocab_size=1000) and
      feeds them into routing_key_proj as if they were hidden states -

   Suggested fix: feed the layer's actual hidden states (hook the layer

6. MEDIUM - GRPO example claims PPO clipping; the code has neither a
   probability ratio nor clipping, and its "accuracy" counts format-only
   rewards. [static]
   File: examples/train_weft2_grpo.py.
   - Docstring (line 11) and signature (line 52, clip_eps=0.2) advertise
     L_clip = min(r_t A, clip(r_t, 1-eps, 1+eps) A). The objective at
     line 121 is loss = -(advantages * seq_log_probs).mean(): no stored
     old-policy log-probs, no ratio r_t, no clipping. clip_eps is never
     used (verified by grep: only grad-norm clipping at line 125). This
     is REINFORCE with a group baseline, not the clipped objective
     described. Either implement the ratio+clip or reword the docstring.
   - Objective weighting note: seq_log_probs is the SUM of per-token
     log-probs over each completion, so each completion enters the mean
     with magnitude proportional to its generated length. Per-token
     normalization (dividing by completion length) is the common
     alternative; this is a design choice to make deliberately and
     document, not asserted to be wrong.
   - Line 131: acc = mean(r > 0.0). MathRuleVerifier gives up to 0.5 of
     format reward with ZERO accuracy (verifier.py: format_reward up to
     0.3 + 0.2), so "Group Acc" prints as high as ~50% for completions
     that are entirely wrong. Use res.accuracy_reward == 1.0.
   Note: the eaa7c69 fix itself (float(true_ans) into verify_solution)
   is correct and matches the verifier signature.

7. LOW - Serving tokenizer fallback crashes for char-vocab checkpoints
   missing vocab.json; CORS config is suspect. [tokenizer reproduced

   File: weft/serving_server.py.
   - Line 77: engine.tokenizer = WeftCharTokenizer() raises
     TypeError (missing required vocab_file) - reproduced here. Hit only

10. LOW - MoE associative routing state handling is inconsistent across
    cache modes and prefill/decode. [static; one probe measured]
    Files: weft/modeling_weft.py:548, weft/moe.py:119-121 vs 134-135.
    - Router state is only threaded when the past is an HF Cache
      (modeling_weft.py:548); with tuple past_key_values the router
      memory silently resets to zeros every forward.
    - Prefill accumulates the router state from the STATIC-router
      softmax (moe.py:134-135) while decode accumulates from the
      COMBINED static+associative softmax (moe.py:119-121). In a probe
      at random init, full-forward and prefill+decode logits agreed to

      it grows with the associative term. Pick one rule for both paths.

      sequential routing scan from a zero state on every forward - an
      O(S) Python loop per MoE layer per step. Fine at seq_len=128;
